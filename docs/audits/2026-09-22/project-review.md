# 资料整理助手：产品、UI 与抓取链路全面评审

日期：2026-09-22。代码基线：HEAD `5c273ef8` 加当前工作区未提交修改。

## 结论

这个项目有明确价值：把分散在工单、文档、代码讨论和聊天中的工作信息，保存为可追溯、可持续更新的个人知识库。当前最需要改进的是**用户对“保存成功、抓取完整、更新可见、回答有依据”的信任**。界面重设计应围绕这条链路展开。

现有版本功能广度已超过早期 MVP，但核心数据契约和状态语义没有同步成熟。抓取方式、来源类型、订阅任务、资料版本、AI 整理、未读更新彼此耦合，结果是：有时数据抓到了但用户看不到更新，有时显示成功却没有抓到子页面，有时隔离资料仍进入 AI 检索。

建议保留本地优先、可读文件、来源证据、浏览器登录复用、快照和差异这些基础能力；优先修复正确性，再把产品收敛成“收集 → 跟踪变化 → 阅读／提问 → 回到证据”的日常工作循环。没有必要先更换前端框架或整体重写。

## 1. 从使用者出发，重新定义产品

### 用户实际要完成的事

1. “这条信息以后可能用到，帮我收下。”用户不想先判断 API、WebDriver、列表页还是内容页。
2. “这些问题／讨论有进展时让我知道。”用户关心发生了什么变化，而非任务跑了多少轮。
3. “我现在要做判断，帮我找齐证据。”用户需要知道答案来自哪里、资料有多新、有没有漏抓。
4. “抓取失败了，告诉我做什么能恢复。”用户需要重新登录、打开 VPN、重试失败部分等具体动作。

目前首页更像抓取运行面板，资料页更像内容维护表单，订阅页更像任务配置器。工程人员能理解，但日常使用需要反复在模块之间翻译自己的意图。

### 推荐的信息架构

| 一级入口 | 面向用户的内容 | 移入或合并的现有能力 |
|---|---|---|
| 工作台 | 未读变化、需要处理的问题、最近阅读、全局搜索／提问 | 首页、更新提醒、简化的数据源状态 |
| 资料库 | 搜索、筛选、阅读、原文与整理版、差异与历史 | 资料整理、标签和批处理 |
| 关注来源 | 连接状态、关注规则、同步范围、最近结果、失败恢复 | 订阅管理、设置中的抓取配置 |
| 问答 | 有会话上下文的资料问答、范围选择、可点击证据 | AI 对话 |
| 设置 | 模型、数据位置、备份、通知、个人／项目背景 | 设置、补充资料 |

“添加资料”成为全局主按钮，不必独占一级导航。“补充资料”按个人／项目背景定位，用户主动编辑；自动建议保留待审核状态、依据和适用范围，不直接作为普遍事实。

工作台空库时显示“保存第一条资料”及少量可选示例；有资料后优先显示可行动的信息，例如“3 条关注内容有变化”“1 个来源需重新登录”。数据总数、存储大小、运行进度降为次要信息。

### 建议的核心页面布局

```text
工作台                          [搜索或提问……]  [+ 添加]

需要你处理
  Jira 登录失效                 [重新登录]
  Teams 本次只捕获最近 40 条     [查看范围] [补全]

关注内容的变化
  ISSUE-123 状态从处理中变成完成 [查看差异]
  设计讨论新增 3 条回复          [阅读新消息]

最近阅读                        来源状态摘要
```

这是一种任务优先布局。是否采用侧栏、顶部导航或抽屉可以调整，核心是第一屏能回答“我现在该做什么”。

## 2. UI 和交互的具体问题

### 首页：状态表达不可信，行动优先级不足

实测全新空库仍显示“混合检索”“联网资料”；没有启用 embedding，也没有验证来源连通性。默认还出现一个企业 Jira 过滤任务。无运行记录的数据源显示质量 100 分；“最近成功”列出现 0%。这些表达会让用户误判配置和同步状态。

对应：`public/index.html:102` 附近的静态状态、`src/server.js:8034` 默认设置、`src/reliability.js:42` 健康计算、`public/app.js` 首页任务渲染。

建议：能力状态由后端实际配置与最近验证结果驱动；“尚未检测”独立于“健康”；首次运行不创建真实企业订阅；取消没有明确解释和校准的综合质量分。最近成功用时间，当前运行进度只在运行时显示。

### 添加资料：把自动识别变为默认工作流

当前一屏要求理解来源、抓取方式、页面类型、URL、原始输入、过滤内容、总结。预览是两列编辑器，适合排障，不适合作为默认收集体验。

建议流程：粘贴链接／文本或选文件 → 自动识别并展示结果 → 保存。抓取方式、页面类型和原始响应放入“高级选项”。预览首先显示可阅读内容和完整性说明，编辑器按需展开。

识别到列表时明确显示“关注这个列表”，按钮写“创建关注”；保存单页时让用户选择“一次保存”或“持续关注”，显示默认值及后果。重复链接提供“打开已有资料”“检查更新”；避免解析结果里的编辑字段可以修改，但确认动作实际上只是打开已有资料。

实际代码还有两个交互问题：确认导入没有统一的提交中状态和错误兜底；自动预览只阻止旧响应更新 UI，没有取消正在执行的抓取。应防重复提交，并让慢任务可取消、可恢复。

证据：`public/app.js:2700`、`:2768`，`src/server.js:578`。

### 资料详情：先阅读，再管理

实测一条短文本上方排列保存标题、AI 标题、模式开关、AI 整理、标签、刷新、差异、删除等控件。未生成整理版时开关仍标注“已整理”，下方再解释实际上显示原文。`text / local input / manual / no tags` 等内部值也直接进入 UI。

建议默认只保留标题、来源、更新时间、内容和少量主操作。标题点击后编辑；删除和低频操作进入菜单。“原文”“整理版”“变更”使用标签页；整理版不存在、正在生成、已过期都明确表达。AI 按钮在未配置时提供配置入口；本地文本不显示无意义的来源刷新动作。

资料列表应有摘要、来源、更新时间、未读／不完整标记，帮助用户选中正确的条目。保留阅读位置与筛选状态；支持可复制的资料深链接和浏览器前进／后退。

`selectItem` 没有在响应回来时确认仍是当前选中项，快速点击 A、B 时，慢返回的 A 可以覆盖 B 的详情。点击资料还立即确认更新已读，无法区分“打开过”和“已处理”。建议引入请求版本校验，已读与待处理分开。

证据：`public/app.js:1698`、`:1734`。

### 布局应给阅读让出空间

详情截图约 1200 像素宽，侧栏、资料列表和详情同时占据宽度，正文栏仅约四百余像素，底部出现横向滚动。左侧仅一条资料时仍保留大片空白，右侧操作却折成多行。建议支持可调宽列表／详情、收起导航和专注阅读；窄屏分层进入列表和详情。按钮主次、空状态、加载骨架、键盘焦点、弹窗焦点归还应使用统一规范。此轮没有完成手机和全键盘实测，不能把已有 CSS 媒体查询等同于可用性通过。

### 后台更新不能打断输入

`public/app.js:3669` 和 `:3873` 都安排 1.2 秒后 `window.location.reload()`。后台轮询也可能触发。用户正在写问题、改标签、编辑导入结果时，会被整页刷新打断。

订阅页另有每分钟重绘任务表单的路径，可能覆盖尚未保存的编辑（`:3683`）。

建议按实体更新缓存和列表，保留当前草稿；发生冲突时显示“来源已更新”，让用户决定何时载入。订阅开关与频率采用逐项保存或明确的脏状态；轮询只更新运行状态字段。

### 问答需要符合“对话”的预期

`public/app.js:2397` 只发送 `{ message }`；`src/server.js:2388` 只构造本轮问题和检索结果。页面虽然保存会话历史，模型并不知道上一轮问了什么，“那它后来怎样了”无法可靠指代。

同时没有会话级取消控制；切换会话后，旧请求的流式回调仍向当前 DOM 追加内容。应将请求、会话和消息 ID 绑定，支持停止生成、重试、切换后后台继续或明确取消。

默认把检索过程折叠成“找到 5 条资料”，详细日志按需查看。“显示思考过程”应改为“显示检索步骤”，因为这里展示的是固定过程事件。答案旁显示资料版本、片段定位、同步时间和缺失范围；空库或无命中时给具体的下一步。

## 3. 必须优先处理的实现问题

下列 P0 指阻碍可信使用、应优先修复，并非宣称发现了公开可利用的最高级别漏洞。

### P0：API 列表返回格式与消费方不匹配

**代码与样例确认。** Jira REST 返回的 `raw` 是搜索结果 JSON，GitHub notifications 的 `raw` 也是 JSON；`refreshListJob` 却调用 `extractContentLinksFromList(listFetched.raw, ...)`，Jira 分支寻找 HTML 表格／锚点，GitHub 分支寻找 HTML 列表节点。

样例中一个 issue／notification 均提取出 **0 条链接**。实际影响是 API 成功后，列表刷新可能被记为成功但没有导入内容页。真实企业端到端尚未运行。

证据：`src/server.js:4073`、`:4755`、`:4783`、`:4865`、`:6383`。

修复：抓取结果直接返回规范化 `entries`，保留 `raw` 仅供证据存档。列表消费者不应再推断或解析传输格式。API／HTML／浏览器适配器都输出同一结构，并保留分页范围。

### P0：向量路径绕过检索过滤和资料隔离

**接口复现。** 关键词分支应用隔离、来源、标签、时间和远程 AI 限制；向量分支没有收到这些过滤参数，合并时也没有再过滤。

在本机模拟 embedding 服务后，查询不存在的标签，仍返回了全部 5 条测试资料，其中包含隔离资料。隔离内容也进入 embedding 请求。

证据：`src/server.js:2471`、`:2582`、`:2691`、`:2708`。

修复：在分块／向量生成之前执行内容使用策略；关键词和向量召回共享过滤条件；最终返回前再次校验。隔离／权限变化必须使索引资格失效，不能只依赖正文修改时间。

### P0：远程 AI 开关不是统一的出站约束

**代码确认，未向远程服务发送测试数据。** `isRemoteAiAllowed` 只用于整理正文和关键词问答过滤。标题、标签、分类等路径没有统一检查；embedding 建索引也没有检查，并且判断函数只看聊天模型地址，不看 embedding 地址。

用户取消“允许将该来源的相关片段发送到远程 AI”，无法据此确信所有功能都遵守。UI 的“尚未配置 AI；资料不会发送到模型服务”也没有覆盖独立启用远程 embedding 的情况。

修复：所有模型出站统一经过策略入口，以实际目标端点、资料集合、用途执行检查。策略拒绝应在发送前失败，并在 UI 说明哪些资料被排除。补充背景和 AI 建议语料同样适用。

证据：`src/server.js:1573`、`:1642`、`:2092`、`:8360`，`src/ai-client.js`。

### P0：Teams 增量消息可能被静默丢弃

**接口复现。** 已有 12 条消息，本次抓取末尾 3 条旧消息加 1 条新消息，结果仍只有原来的 12 条，新消息未保存。

原因：`mergeFetchedTeamsInputWithExisting` 遇到“旧消息至少 10 条且本次数量更少”直接返回旧消息集合。这个保护适合阻止不完整覆盖，却不适合处理正常的局部增量捕获。

修复：先验证会话身份，再按稳定消息 ID 合并。局部捕获不能据此删除未出现的旧消息；同 ID 的编辑按版本更新；删除需权威删除标记或完整覆盖证据。没有稳定 ID 时明确降低置信度，不能把临时 DOM 位置当永久身份。

证据：`src/server.js:1098`、`:5916`。当前合并键是“时间 + 正文”，没有充分表达编辑、删除与不同发送者的同文消息。

### P1：用户脚本捕获未经验证就标记 verified

**接口复现。** `/api/items/upsert-capture` 对 sourceType=teams 直接设置 `integrityStatus: verified`，没有走刷新路径的会话身份验证。任意测试标题和消息也获得 verified。

用户脚本捕获的是当前 DOM 可见内容，上限 240 条；fingerprint 只含 URL、数量和最后消息信息，修改中间消息可能不触发同步。脚本还上传整个页面 HTML，存储量及证据范围都过大。

建议把此类能力命名为“同步当前会话可见消息”，保存身份依据、捕获区间和 partial 状态；把手工浏览器捕获与无人值守后台同步区分开。不要要求用户以是否弹窗来推断同步模式。

证据：`src/server.js:1022`，`userscripts/teams-auto-capture.user.js:18`、`:41`、`:63`。

### P1：整理版的新鲜度和 NEW 被错误耦合

**部分接口复现，其余代码确认。** 资料已处于 `processedStale: true` 时，一次内容不变的抓取把它重置为 false。用户可能继续阅读过期整理版而看不到提醒。

另外，原文变化先写入 `pendingContentUpdatedAt`，只有 AI 整理成功才转为 `contentUpdatedAt`；未配置 AI 会得到“刷新内容已暂存，未显示 NEW”。资料更新与付费／可用模型不应有这种依赖。

修复：原文版本、整理版对应的原文版本、用户已读版本分别记录；原文变化立即产生更新事件。整理失败仅表示派生内容未更新。重复抓取不能清除已有过期状态。

证据：`src/server.js:852`、`:939`、`:2092`、`:3763`，`public/app.js:1129`。

### P1：桌面启动端口与持久化／浏览器捕获不兼容

**代码推导，未运行打包桌面版。** Electron 每次找随机端口，聊天和偏好却保存在页面 localStorage；端口变更会切换 origin，旧历史不再从新 origin 可见。这不是证明磁盘数据已删除，而是用户体验上历史失联。

用户脚本固定发送到 8020，也无法自动连接随机端口的桌面服务。macOS 关闭窗口后 activate 对已销毁窗口调用 show 的路径也应实测修复。

修复：会话由应用数据目录持久化，页面通过 API 访问；为外部捕获设计配对和服务发现，或固定且可验证的本机入口。不要把所有问题仅归结为“换成固定端口”，还需处理端口占用和连接错实例。

证据：`desktop/main.js:31`、`:61`、`:136`，`public/app.js:2567`、`:2683`，用户脚本 `:18`。

## 4. 抓取系统的整体设计

### 抓取结果需要表达事实，而不仅是 text

建议规范化契约：

```text
CaptureResult
  sourceIdentity: provider / tenant / resourceType / resourceId
  requestedUrl / canonicalUrl / finalUrl
  method: api / http / browser / user_capture
  title / body / comments / entries
  fetchedAt / sourceVersion / validators
  completeness: complete / partial / unknown
  coverage: timeRange / cursor / observedCount / expectedCount
  identityEvidence / warnings / rawArtifact
```

`CaptureResult` 是来源观察结果；`MaterialRevision` 是通过校验后提交的事实版本；`ProcessedArtifact` 是绑定版本的 AI 产物。预览、导入、直接刷新、订阅刷新、用户脚本应进入同一校验／提交入口，避免某条路径有保护、另一条绕过。

### 各来源的边界

| 来源 | 当前主要不足 | 目标行为 |
|---|---|---|
| Jira | 固定域名；过滤查询和评论使用单次 maxResults，未闭合分页；列表 JSON 契约问题 | 实例能力配置、结构化条目、游标／分页、明确已抓数量和是否截断 |
| Confluence | 评论取一次 limit=200，失败吞成空集合；正文 storage 中宏内容未必完整 | 评论失败显示 partial，保留已有评论；宏／附件保留引用和缺失说明 |
| GitHub | REST PR 只收普通 issue comments，未覆盖 review comments／reviews；HTML 与 API 完整性标准不同 | 分对象声明覆盖范围，不能用“API 成功”代表完整讨论已抓取 |
| Teams | Graph 存在但常规 auto／WebDriver 路径跳过 Teams API-first；浏览器确认与虚拟列表增量复杂 | 能力探测后选择受支持通路；可见窗口捕获明确标部分；会话 ID 优先 |
| 普通网页 | 通用 Readability 回退；fetch 失败并非统一升级到浏览器 | 先低成本提取，按失败类型选择登录、浏览器、手动粘贴；保留实际方法和证据 |

以上是当前代码覆盖范围的审查，不代表已验证各服务最新 API 的兼容性。

通用分页 `requestSourceCollection` 最多 20 页／1000 条，但返回值没有明确 truncated 和剩余游标。限制本身合理，静默宣称完成不合理。用户配置“最多 50 条”应被表达为范围策略，不能和抓取失败、服务端上限混为一谈。

API 失败当前大多统一告警后回退。应区分未登录、无权限、不支持、限流、网络故障、解析失败；保留各次尝试及采用原因。限流应尊重退避信息，身份不匹配必须停止，不能用较弱提取路径掩盖。

### 认证与浏览器资源

优先自动选择可用的认证通路。即使最后可以用 API，当前刷新批次仍可能先创建浏览器并做认证预检，造成不必要的窗口和失败点。

按“来源账户／浏览器会话”而非仅 job ID 加锁。多个任务可能共享一个 page，预览、手动刷新、订阅批次会争用导航；现有 running/queued 集合不能覆盖全部入口。需要会话租约、任务独立页面或按会话串行队列。

不要以固定企业域名作为适配器注册机制。来源实例应配置产品类型和实例根地址，必要时能力探测；已支持的域名作为迁移配置保留。

### 调度、取消和故障恢复

- 执行记录应可持久化恢复，并分 pending、running、waiting_for_login、partial、succeeded、failed、canceled。
- 用户取消现在主要设置 cancelRequested 并关闭浏览器；HTTP/API 活动请求没有接入同一个取消信号，仍可能在当前任务结束前写入。将取消信号传递到抓取、分页、AI 和提交前校验。
- 普通 HTTP 抓取在收到 headers 后即清除超时，正文读取仍可能长时间挂起；12 MB 检查部分发生在整包读完之后。改成读取流时累计字节并执行总截止时间。
- AI 客户端没有显式超时和 AbortSignal；与刷新后自动整理串联时，抓取完成也可能长期等不到批次完成。
- 跨午夜时间窗口样例 `22:00–06:00`、凌晨 01:00 返回不该运行；应依据跨日窗口起点计算。
- 重试只重试失败条目，保留成功结果；页面显示“成功 18、失败 2、部分 1”，不要只给一个绿色完成。

证据：`src/server.js:3082`、`:3240`、`:3277`、`:3470`、`:3967`、`:4597`、`:4700`、`:4731`，`src/ai-client.js`。

## 5. 存储、检索和维护性

### 保留文件可读性，同时补足提交一致性

当前 raw、metadata、comments、document 逐个覆盖写入，没有事务边界；失败时可能只更新了部分文件。并发同 URL upsert 也没有唯一约束／对象锁。单条损坏 JSON 或缺失 document 可以让 list/rebuildIndexes 抛错，启动时又会重建索引，扩大影响。

先引入每条资料的写锁、临时文件／版本目录、提交标记和可恢复 journal；索引失败不应使已提交内容不可读。后续若并发、关系和检索规模需要，可用 SQLite 管理元数据、任务和全文索引，正文／原始证据仍保留文件导出。采用数据库是条件性选择，不是重构的前提。

### 备份导入要先校验后提交

replace 先重命名旧库再逐条校验写入；中途失败虽保留 backup，却没有自动回滚。merge 也可能部分覆盖。导出把所有文件读入内存并 base64 编码，大库成本高。

建议在 staging 目录完整校验格式、路径、大小、引用和索引可建性，再交换生效；merge 明确冲突策略。导出采用流式归档和清单校验，备份还原必须有一次完整往返验证。

证据：`src/server.js:7870`、`:7956`，`src/item-store.js:110`、`:180`。

### 检索性能和质量需要分别解决

列表接口虽然有分页，仍先扫描并读取全库正文；前端不少调用不传分页。每次更新重建全量索引，批量 N 条会重复做 N 次全库工作。现有 search.json 只含摘要，另一条 knowledge-search 又读全量内容，两套搜索命中规则不同。

embedding 在问答时校验全库 manifest，任何变化可能触发全量重建；每条最多前 20 块，长讨论尾部容易缺失。应后台按内容哈希增量更新，支持索引状态／取消／成本预估，查询不承担全库建索引工作。

关键词／向量合并需要使用同一资格过滤，避免陈旧 AI 整理版压过最新原文。对用户问题做检索评估集，覆盖中文自然问句、工单号、作者、相对时间、别名、后续追问、无答案和冲突证据。先测真实召回，再决定是否需要更复杂的排序模型。

证据：`src/item-store.js:126`、`:258`，`src/server.js:2471`、`:2667`、`:2708`。

### 本机接口也需要明确调用边界

本次对独立测试服务发送带外站 Origin、text/plain 的 POST 仍创建了资料。服务端未统一校验 Origin 或应用凭证；绑定 loopback 限制了网络可达范围，但不能独自表达哪些调用方被允许。

建议桌面／网页 API 有来源校验和会话凭证，外部用户脚本使用专门配对 token；限制请求体和抓取协议。此处不把命令行请求成功等同于所有浏览器都可跨站攻击，浏览器网络策略仍是另一层。

### 拆模块应围绕变化原因

当前 server.js 8476 行、app.js 4185 行、styles.css 3173 行。体积不是唯一问题，更关键的是多条抓取和写入路径重复组合不同保护逻辑。

建议边界：

```text
HTTP API → 应用服务 → 抓取协调 / 资料版本 / 更新收件箱 / 问答
                       ↓
             来源适配器 / 认证与浏览器 / 存储 / AI 出站策略
```

前端按工作台、资料库、添加流程、关注来源、会话分别拥有状态；共享请求层处理取消、错误和数据缓存。先建立契约与行为测试，再逐步迁移函数，避免把大文件原样切碎后继续保留原来的耦合。

## 6. 实施顺序和验收条件

| 阶段 | 交付内容 | 完成判据 |
|---|---|---|
| A：可信性修复 | API 列表 entries、统一 AI 策略、Teams 增量／身份、整理过期状态、取消强刷 | 本报告已复现问题全部有行为回归测试；失败／部分结果不伪装成功 |
| B：用户流程 | 全局添加、工作台更新收件箱、阅读优先详情、关注来源、真实会话 | 新用户不配置 AI 也能保存／搜索／看更新；后台同步不丢草稿；一次登录后能看见明确连接状态 |
| C：执行与存储 | 任务队列、会话资源锁、提交一致性、导入回滚、增量索引、桌面持久化 | 中断／重启可恢复；并发同源不串页；导入失败恢复旧库；重启后会话保留 |
| D：扩展与体验 | 通用来源实例、更多内容覆盖、大库优化、窄屏和键盘操作 | 每种来源有覆盖矩阵和样例；规模基准达标；关键动作可键盘完成 |

不建议把“UI 大改完成”作为第一阶段成功标准。首先应有能被界面诚实呈现的数据和状态。

### 必须补充的测试场景

1. API 返回 3 条列表记录，刷新最终导入 3 个内容实体；验证后续页、截断、空列表和 304。
2. 关键词、向量、混合模式下，相同标签／来源／时间／隔离条件得到相同资格集合；被禁止内容不进入模拟模型请求。
3. Teams 全量后局部增量、消息编辑、删除、同名不同会话、重定向和身份不符；保留旧证据但不混入错误消息。
4. 原文变更后 AI 失败仍可见未读更新；重复无变化抓取不清除过期状态。
5. 取消抓取后不再提交当前任务的新版本；响应体慢流、429、登录失效能结束且有明确状态。
6. 切换会话／资料时旧请求不污染新界面；后台更新不丢输入；重复点击导入不生成重复资料。
7. 写入中断、单条损坏、导入中途失败、备份恢复；桌面重启和 macOS 重新打开窗口。

现有 29 项测试适合作为工具函数基础，其中 server-regressions 主要正则匹配源码，无法验证上述结果。可以保留少量结构保护，但应以 fixture、模拟 HTTP 服务、临时知识库及用户流程测试为主。

## 7. 需要保留的设计资产

- Markdown／JSON／JSONL 的可迁移性和可检查性。
- 原始来源、评论和快照的证据链。
- 登录态复用、API 与浏览器多通路的方向。
- 将原文与 AI 整理版分离，而非不可逆覆盖原文。
- 对跨会话、评论退化和隔离问题已经建立的防护意识。
- 语法检查和基础测试基础设施。

最终产品承诺建议收敛为：**把你关注的工作资料可靠地收下来，让变化可见，让每个回答都能回到证据。** UI、抓取、调度、AI 和存储都应按这句话验收。
